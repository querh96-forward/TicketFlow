# 约5分钟演示稿

演示前运行 `docker compose -p ticketflow ps`，打开 <http://127.0.0.1:6010>。右上角显示当前模型模式；真实模型耗时受服务影响，建议保留一份已经完成的任务用于回放。

## 1. 介绍场景（30秒）

“这是一个企业工单协作系统。它将账号问题和平台问题交给不同专家调查，经过独立审核和人工批准再处理工单。重点是多Agent的权限、上下文和任务状态如何协调。”

## 2. 创建并分析工单（约1分钟）

点击“新建演示工单”，选择账号锁定或导出失败，再点击“开始协作分析”。展开角色调查的详细记录。

“账号与平台专家使用不同工具，只查询当前工单绑定的事实。协调员通过Deep Agents的task工具委派；两个独立调查可以并行。每位专家将结果保存为证据编号，而不是不断转发完整聊天历史。”

如果使用确定性演示模式，应明确说明：“这里用固定模型决策演示流程，图、工具、数据库和审批机制是真实运行的；真实模型结果另外看评测记录。”

## 3. 展示审核与批准（1分钟）

等待出现审批面板，展开证据与方案编号。此时业务工单还没有改变。

“审核Agent检查方案和证据，只能提出审核意见。真正执行之前，流程通过LangGraph中断暂停，审批内容和检查点都已持久化。”

点击“批准并执行”，观察完成记录和工单状态。

“批准绑定当前方案编号。执行器还会核对业务条件、工单版本和审批记录。重复请求会读已有操作回执，不会再次修改业务。”

## 4. 展示退回与恢复（约1分钟）

新建另一张账号锁定工单，待审核完成后填写“不要恢复访问，转人工核查”，点击“退回修订”。新方案应重新审核和审批。

如需展示重启恢复，在任务**等待审批**时执行：

```bash
docker compose -p ticketflow restart app
```

服务恢复后刷新页面，从“最近任务”打开该任务，再批准。不要把等待审批的时长算作模型执行耗时。

“重启后仍使用原任务和检查点，不会丢失已经完成的调查。旧的审批编号只在对应等待状态下有效。”

## 5. 说明评测和边界（30秒）

“机制通过自动化测试覆盖，真实模型另外跑少量固定场景。评分关注审批前是否没有执行、执行动作是否正确、是否只执行一次。当前连接的是演示业务库，未接入真实账号或工单平台，也尚未证明多Agent比单Agent更省成本。”

## 工单管理与协作追踪

- 选择工单，在详情中点击“删除工单”，确认“移入回收站”；切到“回收站”，选择工单后点击“恢复工单”。历史协作记录仍可查看。活动任务须先结束，或取消排队/待审批任务。
- 打开“最近任务”的完成记录，在协作轨迹上方查看各角色的调用、Token和累计耗时；选择“账号权限专家”等角色筛选时间线。
- 点击“导出任务报告”下载JSON，包含该任务的证据、审核、操作回执与完整审计事件。旧任务没有模型名称记录的部分会明确标注。
- 可以讲：“通过关联编号把一次模型请求与结束或失败事件对应起来，判断成本和错误来自哪位专家。多个专家并行，所以角色调用耗时之和不能直接当作用户等待时长。”
