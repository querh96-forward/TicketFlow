# 审核意见落库后才能完成交接 · 2026-10-02

## 行为变化

审核员可能只输出“审核通过”，没有调用 `record_review`。此前协调员会拿到这句文字，随后请求审批时才被系统拒绝。

现在审核子Agent在准备返回最终文本时运行 `PersistedReviewGate`：

1. 从委派任务中识别唯一方案编号，并检查属于当前任务。
2. 查询该方案的数据库审核记录。已保存同意或拒绝均视为审核完成。
3. 没有记录则最多提醒补交一次，要求模型使用真实工具读取方案、保存意见；程序不代填结论。
4. 再次返回最终文本仍未保存时，停止交接，任务进入 `needs_attention`，标记 `REVIEW_NOT_RECORDED`，不生成审批卡。
5. 有记录时，只将数据库中的实际审核结果返回协调员；模型口头同意不能覆盖已保存的拒绝。

后续仍执行原有人工审批和事务约束。若业务已产生回执，后续交接异常保留 `completed_with_warning` 和真实回执，不能误报未执行。

## 提醒次数、预算与恢复

`review_repairs` 按 `(run_id, proposal_id)` 唯一记录补交提醒及原模型消息编号。事务内领取额度避免并发重复；同一消息的检查点重放幂等，新消息不能再次领取同一方案额度。重启或重试不清空记录；修订后的新方案有自己的额度，但方案总数仍最多三个。

补交继续走原Agent图和 `AuditBudget`，模型调用、Token和超时不重置。一次提醒后可能需要多步工具操作，不意味着只增加一次模型调用。若先耗尽预算或遇到服务异常，保留原有失败诊断，不绕过限制强行完成审核。

时间线新增“提醒补交审核意见”“审核未落库，交接已停止”事件。

## 对照实验边界

新校验用于多Agent的独立审核交接。单Agent没有独立审核子Agent，继续使用原有自检保存和审批检查。两者不再仅在角色结构上存在差异，报告必须同时说明多Agent新增了有限补交机制；相同模型和总预算不等于完全相同的控制策略。

故障注入测试验证异常机制，真实模型回归验证具体运行结果；两种证据不混为“模型准确率”。人工批准和拒绝由脚本按预设场景模拟，作用于临时演示库，并非真实用户审批。
