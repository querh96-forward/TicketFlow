# 实现说明与面试要点

## 为什么是多Agent

账号专家只接触账号状态与授权事实，平台专家只接触作业、错误和事故状态。这两类调查互不依赖，可以并行；它们的工具能力不同，因此拆分有明确的权限和上下文边界。审核员读取方案和结构化证据，检查动作是否合适，不能执行动作。

主Agent使用Deep Agents的 `task` 工具委派三个 `CompiledSubAgent`，子Agent通过LangChain `create_agent` 构建。它们是真实的独立工具调用循环，不是界面中用三个名字标注同一轮模型回答。多个角色可以使用同一个模型服务，不要求不同模型或不同进程。

简单工单使用单Agent可能更省时省Token。项目已增加同题、同模型、同预算的单Agent对照，方法和限制见 `docs/comparison-method.md`；不能由多Agent结构本身推断准确率或成本收益。当前价值集中在权限划分、证据交接、独立审核和审批后的动作一致性。

## 框架能力和应用实现

| 框架提供 | 本项目实现 |
|---|---|
| 子Agent委派与独立上下文 | 角色职责、限定工具、双专家证据要求、审核流程 |
| LangGraph Checkpoint与中断恢复 | 持久化运行记录、审批API、过期审批拒绝、页面交互 |
| 工具调用与流式运行基础 | SQLite审计事件、SSE游标回放、角色与用量显示 |
| 上下文压缩基础设施 | 摘要长度约束、结构化事实、精简工具回包；首版未用长任务验证自动压缩效果 |

默认通用子Agent与文件系统/命令执行工具被关闭，避免额外角色获得业务工具。业务执行只暴露给协调员，专家没有嵌套委派或执行权限。此限制属于应用工具边界，不靠“请不要越权”的Prompt单独保障。

## 状态与数据

应用数据位于 `tickets.sqlite`，图检查点位于 `checkpoints.sqlite`，二者均在Docker数据卷内。

- `tickets`：演示业务事实、状态、版本。
- `runs`：任务状态、事实快照、待审批信息、恢复指令、模型调用数和Token用量。
- `findings`：专家摘要、运行内证据编号。读取时附加该角色的结构化事实快照。
- `proposals`：方案与证据快照。审核意见首次写入后固定；新方案需要重新审核。
- `decisions`：人工决定，绑定审批编号和方案编号。
- `operations`：以方案编号为唯一键的执行回执。
- `events`：持久化事件序列，支持SSE断线后按游标补发。

运行状态：`queued → running → waiting_approval → queued → running → completed`。其他终态包括 `failed`、`needs_attention`、`canceled`，以及业务成功但模型总结失败的 `completed_with_warning`。

## 人工介入与一致性

`interrupt_on`只拦截 `execute_resolution`。先完成调查和审核，再向用户展示具体待执行方案。批准或拒绝由API写入数据库；Worker使用中断编号和 `Command(resume=...)` 继续同一个图实例的持久化状态。

审批接口在事务内检查任务状态和当前审批编号，防止重复点击、并发批准和旧页面提交。拒绝后如果模型提出新方案，会生成新编号、重新审核并再次请求审批。

真实模型曾仅输出“请批准”的文字而没有调用审批工具。现在提示词明确工具调用与实际执行的区别；若图结束时存在已审核但尚未请求审批的方案，运行器最多追加一次纠正消息，要求模型调用工具。仍未产生中断时进入 `needs_attention`，不会伪造工具调用或批准。

未过期的失败或需要人工处理任务可从页面点击“从检查点继续”；累计调用和Token预算不重置。快照过期任务必须启动新任务，不能从旧检查点恢复。已经产生业务回执的任务不能重新执行。模型最终总结失败但业务事务已成功时标记 `completed_with_warning`，展示确定性的业务回执，避免把已完成的操作误报成未执行。

执行器的事务先查操作回执；若已经执行，直接返回已有结果。否则检查：任务正在执行、方案属于本任务、审核通过、人工批准、工单版本未变化、动作满足业务策略。业务修改与回执写入使用同一个SQLite事务，避免只写其中一项。

图检查点与业务事务没有跨库原子提交，所以不能声称分布式exactly-once。对于当前本地业务库，可以通过回执去重使检查点重放不重复修改业务。接真实外部系统时，需要外部幂等键、Outbox或补偿机制。

单Worker使用操作系统文件锁防止多进程同时恢复任务。重启时把遗留的 `running` 任务重新排队，再检查图状态；已暂停的审批保持等待。应用层最终状态未写入但图已完成时，恢复只读取已有结果，不再重复调用模型或业务动作。

## 上下文收敛

首轮真实模型调查出现长篇重复报告，进入审批前累计68,424 Token。这个开发观察保存在 `evals/reports/initial-context-observation.json`，当时未批准执行，随后取消，不算成功完成样本。

随后采取：专家摘要和审核理由建议180字以内、工具参数限制400字符、最终交接只返回编号与短结论、方案创建只返回编号和动作、移除当前固定业务流程不需要的待办工具。完整证据保存在业务库，审核时按编号读取。这是应用侧上下文控制，不宣称修改了Deep Agents底层压缩算法。

## 面试中可重点讲的五个问题

1. 为什么拆成专家：工具权限、事实来源与可并行的任务不同；也承认小任务的多Agent额外成本。
2. 如何交接：短摘要加结构化事实、运行内证据编号、不可变方案快照。
3. 人工批准后如何继续：持久化Checkpoint、同一thread_id、中断编号和resume指令。
4. 如何避免重复执行：审批事务和唯一编号、业务版本校验、业务修改与回执原子提交。
5. 如何验证：离线模型替身验证机制、真实模型小规模回归验证工具选择；分别保留证据，不混成模型准确率。

首版没有身份认证、多人角色授权、外部工单系统、分布式调度或通用代码执行沙箱。所有业务动作均为本地演示库变更。

## 工单生命周期与协作追踪（2026-10-01）

工单支持移入回收站和恢复。`deleted_at` 为可空时间戳，旧数据库启动时自动补列；重新初始化内置工单不会覆盖删除标记。软删除保留工单事实、任务、审批、回执和检查点，不等于隐私数据清除。

删除、创建任务、恢复任务都在 `BEGIN IMMEDIATE` 事务内检查工单与任务状态。排队、执行中、等待审批的工单禁止删除；回收站中的工单不能创建或恢复任务。这样即使另一个页面同时提交，也不能产生“已删除工单仍在执行”的状态。取消排队或待审批任务后可以删除；运行中的任务须先结束。

参考 [HelloAgents 可观测性指南](https://github.com/jjyaoao/HelloAgents/blob/main/docs/observability-guide.md) 的事件追踪、统计和导出思路，在已有SQLite事件表上实现应用级角色统计和JSON报告。没有复制其实现代码，也未引入第二套Agent框架。

每次模型调用记录 `call_id`、角色和配置模型名，完成/失败/中断事件共享编号。页面按角色显示调用次数、已返回Token、累计调用耗时、失败及中断次数，可以筛选时间线并导出任务、证据、方案、回执和事件。累计调用耗时含模型客户端重试等待，各角色可以并行，不等于端到端墙钟耗时；硬终止时没有结束事件的调用不能补造结果。历史数据缺少模型名时显示未记录。

错误诊断区分认证、限流、超时、连接、服务不可用、模型请求拒绝、流程约束和其他执行错误。诊断只保存分类、异常类型和HTTP状态，不保存模型请求/响应正文；可重试标记只是诊断建议，不会自动重试业务动作。导出对当前配置密钥、常见密钥字段及Bearer/sk样式文本做脱敏，不能代替对任意个人信息的人工检查。

本轮没有添加通用记忆、额外规划Agent或工具熔断器。当前专家已通过框架隔离上下文、执行已有预算和审批控制；仍应先用真实任务验证新增能力的价值。连接外部企业API后，可以进一步引入按服务统计的熔断与恢复策略。

## 人工决策交接与快照过期收尾（2026-10-02）

审核工具 `read_proposal` 现在从数据库的 `decisions` 表读取本任务的人工决策，返回审批编号、方案编号、动作、决定、反馈和时间。先检查方案归属，再限定 `run_id` 查询，不接受模型理由中的“已批准”自述，不暴露其他任务的决策。审核事件记录本次读取的决策编号，便于复盘。

人工退回并要求转交时，即使原动作仍符合业务条件，也允许提出转人工方案；人工反馈不能越过执行策略。新方案仍须重新审核并取得新的人工批准，旧批准不可继承。

快照过期使用专门的 `StaleSnapshot` 错误及 `STALE_SNAPSHOT` 代码。运行入口、模型调用前、方案创建和审批发布时检查版本；审批发布在事务内检查，实际执行仍保留事务内版本校验。过期后运行器写入确定性的 `needs_attention` 结果，清空待审批与恢复指令，禁止恢复旧任务，并提示启动新任务。页面隐藏该任务的恢复按钮，后端也拒绝直接调用重试接口。

已有操作回执的任务不因为自身执行引起的版本递增而误判过期，仍按原逻辑恢复总结和去重；没有放松业务执行事务的任何条件。新增测试验证重启后的人工决策交接、跨任务隔离、伪造决策不能成为真实记录、过期后零新增模型调用和审批、审批发布竞态、执行事务校验以及新任务确实使用最新事实。

## 审核意见落库后的交接（2026-10-02）

审核子Agent增加 `PersistedReviewGate`。当模型准备以最终文本结束审核时，校验委派中的唯一方案编号及其任务归属，并读取该方案的持久化审核意见。缺失时追加一次补交提示，要求模型读取方案并实际调用 `record_review`；不会由程序代填审核意见。再次以文本结束仍未落库，则抛出明确交接错误，任务转为 `needs_attention`，清空审批与恢复指令。

补交额度保存在 `review_repairs`，按任务和方案唯一，事务内竞争领取。重启或重试不会重置额度；同一模型消息的检查点重放可以幂等地产生同一条提示，不重复记提醒事件。新方案有自己的补交额度，但仍受既有最多三个方案、全局调用/Token预算和总时限约束。

无论模型最终文本如何措辞，返回协调员的都是该方案已保存的同意/拒绝及理由。已经落库的拒绝视为完整审核，不会触发补交，更不会自动改成同意。收到审核同意仍须进入原有人工审批与执行事务。若业务回执已提交后出现交接异常，保持 `completed_with_warning` 并展示真实回执，不能误报操作未执行。

此机制作用于多Agent的独立审核交接；单Agent仍使用原有自检落库与审批校验，没有独立审核子Agent。对照报告需要将这个有限纠正机制列为架构差异，不能称为只有角色数量不同的实验。
