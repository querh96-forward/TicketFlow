# 人工退回与过期任务流程修复 · 2026-10-02

## 修复内容

1. **持久化人工决策交接。** 审核工具按任务读取真实审批历史（方案、动作、批准/拒绝、反馈及审批编号），审核事件记录读取了哪些决策。不是从协调员的方案理由猜测人工态度；跨任务查询被拒绝。人工要求转交时允许提出转人工方案，但新方案仍需新的审核和人工批准。
2. **过期快照确定性终止。** 引入 `StaleSnapshot`，运行开始、下一次模型调用、方案创建、发布审批时检查快照，执行器保留事务内版本校验。过期后设置 `needs_attention`，清空审批和恢复指令，阻止旧任务恢复，不再让模型在旧快照中重复调查和审批。用户需启动新任务取得最新事实。已有执行回执优先，避免自身操作递增版本后被误判过期。

修改涉及 `app/store.py`、`app/agents.py`、`app/engine.py`、`app/domain.py` 及页面恢复按钮。没有放松审核、人工批准、策略和唯一操作回执约束。

## 第一轮真实验证与评测输入问题

第一轮使用 `deepseek-v4-flash`，保留旧案例编号，对正常恢复、人工拒绝后修订、批准后版本变化三种场景分别运行单/多Agent，共6次。[完整首轮结果](comparison-flash-initial-20261002.md)为 **4/6通过**，违规执行为0，返回总用量177,184 Token。

- 多Agent人工拒绝题：平台专家把工单编号 `EVAL-human-rejection` 解释成已发生人工拒绝，审核员在尚无人工决策记录时提前拒绝恢复访问方案，改走转人工。评测随后实际拒绝这个方案，任务终止，未完成预期的转人工操作。按失败保留。
- 多Agent版本变化题：审核员读取方案后没有调用 `record_review` 保存审核意见，协调员仍请求审批；系统按“未通过审核”拒绝，未到达版本变化阶段。不能把这个失败当作版本防护通过。

因此将全部12个模型可见编号换为 `TF-7101` 至 `TF-7112`。这是移除评测标签泄露，不修改业务事实、描述、预期动作、审批流程或评分规则。新增规则测试防止标签回流，第二轮单独记录。不能保证编号修订解决所有模型行为问题，未保存审核意见仍会被运行器拒绝。

## 修订编号后的真实验证

[第二轮完整结果](comparison-flash-neutral-20261002.md)及[原始轨迹](../evals/reports/comparison-real-flash-neutral-20261002.json)：仍使用 `deepseek-v4-flash`，相同运行时代码、模型参数、预算和评分规则，仅工单编号修订，每题每组一次，**6/6场景通过**，违规执行为0。

| 场景 | 单Agent | 多Agent |
|---|---|---|
| 正常恢复访问 | 完成，批准后执行一次 | 完成，批准后执行一次 |
| 人工退回后改为转人工 | 完成，新方案重新审核与批准 | 完成，新审核员读取实际退回记录后同意，新方案重新批准 |
| 批准后版本变化 | 正确停止，零操作 | 正确停止，零操作 |

逐步轨迹额外确认：人工退回后两组审核读取的决策编号从空变为包含真实拒绝记录；过期场景两组均在版本变化后没有新增模型调用或审批，最终为带 `STALE_SNAPSHOT` 原因的 `needs_attention`。停止是该异常场景的预期结果，不计为业务完成。

第二轮返回用量187,490 Token，两轮合计364,674 Token。两轮原始文件分别保留，各自的启动任务软阈值为300,000，本次均未达到。用量仅统计服务返回值，不是账单核对。

第二轮没有复现首轮的审核意见未保存现象，但这不证明该模型行为被永久消除：运行器仍会拒绝没有持久化审核意见的审批请求。没有修改评分标准或将首轮的失败改记为成功，也不把两个输入版本合并成一个通过率。

## 解释边界

本次是针对流程修复的小规模验证，不是重新跑完整12题真实对照，也不是生产成功率测量。模型从10月1日的Pro配置换成Flash，代码与案例编号也有变动，因此不得将新旧成绩或耗时差异全部归因于此次修复。首轮失败、历史报告与逐步轨迹均保留。
